# 1. PRODUCT IDENTITY AND OBJECTIVE

**Product name:** Javadsolvpn

**Platforms:**
- Android phones and tablets.
- iPhone and iPad.
- A shared product design and consistent user experience across both platforms.

**Primary objective:**

Create an elegant, reliable, intelligent VPN client that automatically discovers publicly available connection configurations, validates and organizes them, maintains a secure local configuration repository, selects suitable candidates, and establishes a real VPN connection with as little user effort as possible.

The application should help users access an unrestricted internet connection where lawful and technically possible, including networks that block or interfere with common VPN connections.

It must intelligently select among supported protocols and connection transports instead of relying on a single connection method or a fixed list of hard-coded servers.

The product must prioritize:

1. Genuine connectivity.
2. Connection reliability.
3. Privacy and security.
4. Autonomous recovery.
5. Low resource consumption.
6. Ease of use.
7. A distinctive premium interface.
8. Compatibility with real Android and iOS platform requirements.

Do not promise that every public configuration will work, that unrestricted connectivity is possible on every network, or that all discovered servers are free, safe, anonymous, or reliable.

The product must remain useful when some public sources, protocols, servers, or network transports fail.

# 3. REAL NATIVE VPN ENGINE

Build a genuine device-level VPN application, not a proxy-themed interface.

The selected architecture must provide a real network tunnel on Android and iOS.

On Android, implement and correctly manage the native VPN service using the official system APIs or a maintained engine that correctly integrates with them.

On iOS, implement the appropriate supported Network Extension architecture and Packet Tunnel Provider integration for the selected engine.

Use native Kotlin/Java and Swift/Objective-C components where necessary, even when a shared cross-platform interface is used.

The final architecture may share application logic, models, networking, and interface components, but it must not compromise native VPN functionality.

Requirements:

- Create the virtual tunnel interface.
- Route device traffic according to the selected routing policy.
- Correctly process incoming and outgoing packets.
- Manage the underlying encrypted connection to the selected remote endpoint.
- Track actual engine and operating-system connection states.
- React to permission denial, network changes, revocation, unexpected disconnects, and process lifecycle events.
- Release resources correctly when switching or stopping a connection.
- Avoid overlapping or competing tunnel sessions.
- Support IPv4 and IPv6 according to actual engine capabilities.
- Integrate DNS handling according to the selected engine and platform capabilities.
- Provide sensible MTU and routing configuration.
- Prevent false connection-success indications.

**A successful method call is not proof of a successful tunnel.** Confirm the connection through authoritative native engine or operating-system state, and test actual traffic routing wherever possible.

Never simulate connectivity, fake a public IP change, or mark a connection successful merely because a configuration was found.

The application must not require root access for ordinary VPN functionality.

# 5. AUTOMATIC CONFIGURATION DISCOVERY ENGINE

Create an autonomous discovery subsystem that finds and collects potentially usable public configurations.

The discovery subsystem should support a configurable registry of public sources, including:

- Public GitHub repositories.
- Raw files from public repositories.
- Appropriate public CDN mirrors such as jsDelivr.
- Public configuration collections and indexes.
- Public subscription links provided by the user.
- Other reputable publicly accessible sources discovered during ongoing research.
- Public Telegram pages where access is lawful and available without bypassing authentication or private-channel restrictions.

Research sources rather than relying on a permanently hard-coded handful of endpoints.

The source registry must allow sources to be enabled, disabled, updated, prioritized, tested, and removed.

Store operational metadata such as:

- Source identifier.
- Source type.
- Last successful fetch.
- Last attempted fetch.
- Sanitized source status.
- Last error category.
- Source priority.
- Applicable format information.

Never execute scripts, binaries, arbitrary code, or instructions contained in downloaded source content.

### Discovery workflow

The system must:

1. Check whether local cached candidates remain available.
2. Fetch enabled sources with bounded concurrency.
3. Apply separate timeouts and response-size limits.
4. Handle failed HTTP requests, redirects, rate limits, and unavailable services.
5. Extract supported configuration links and formats.
6. Decode supported encoded configuration formats safely.
7. Parse candidates independently.
8. Validate required fields and supported parameters.
9. Reject malformed configurations.
10. Remove duplicate candidates.
11. Perform appropriate non-invasive reachability checks.
12. Categorize and rank validated candidates.
13. Persist suitable candidates in the local repository.
14. Attempt candidates using the bounded connection strategy.
15. Refresh failed sources later without stopping a working VPN session.
16. Use valid cached candidates if source discovery temporarily fails.

A bad response from one source must never crash the application or prevent results from other sources being processed.

Do not consider a server trustworthy simply because it appears in a public GitHub repository or is returned by a public subscription.

Treat every third-party configuration as untrusted until it passes validation. Even a valid configuration can point to a malicious or unreliable server.

# 8. INTELLIGENT CANDIDATE SELECTION AND FAILOVER

Build an explainable ranking system based on measured results rather than invented scores.

Candidate selection may consider:

- Parser and schema validity.
- Supported protocol and transport combinations.
- Reachability checks.
- Actual connection-establishment time.
- Recent successful tunnel establishment.
- Recent verified connectivity tests.
- Failure history.
- Configuration age.
- Source health metadata.
- Optional user preferences.

Distinguish:

- Host reachable.
- Port reachable.
- Protocol handshake succeeded.
- VPN engine reports connected.
- Actual traffic routing verified.

These are separate states and must not be conflated.

Where practical, perform bounded tests of connectivity, DNS resolution, and traffic routing after connection. Distinguish genuine measured results from unverified metadata.

Never fabricate latency, throughput, country, health, speed, security, or success-rate figures.

### Failure and retry behavior

Set configurable sensible defaults, such as:

- Per-source network timeout.
- Per-candidate connection timeout.
- Maximum number of candidates attempted per automatic session.
- Maximum source retries per discovery cycle.
- Retry cooldown.
- Repository retention and refresh intervals.

Use bounded retries and exponential backoff where appropriate.

If a candidate fails:

1. Record a sanitized failure category.
2. Clean up its resources.
3. Confirm that the previous attempt is no longer competing with the next attempt.
4. Try another eligible candidate.
5. Stop when a verified connection succeeds or the configured limit is reached.

If cleanup cannot be confirmed, do not blindly launch competing connection attempts.

Prevent late or stale callbacks from overwriting the state of a newer connection session.

When every candidate fails, explain the problem and provide a visible retry action.

Do not run infinite background loops or continuously hammer public servers.

### Public configuration limits

Public configurations may disappear at any moment, require credentials, stop responding, reach traffic limits, or be blocked.

The application must handle these conditions honestly. Do not imply that automatic discovery guarantees a stable free connection.
